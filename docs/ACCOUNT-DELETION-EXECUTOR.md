# 계정 활성 데이터 삭제 실행기 · 2026-11-07

로컬 구현·임시 데이터 검증 완료. 운영 미배포, 실행 기능 기본 OFF. 실 사용자 삭제를 실행하지 않았다.

## 범위
- 거래·원장·쿠폰·본인인증·테스트 선정 기록이 없고 연결된 계정이 없는 익명 계정만 대상.
- 프로필/취향/칭호/기기 연결, 식사 선택 기록 및 미선정 신청, 확인된 계정 이벤트, 소유 네이티브 로그인 시도, 이벤트로 연결된 메모리 세션/공유 카드/Duo 정리.
- 오래된 토큰은 UID 해시 폐기 목록으로 거절하며 같은 기기 재가입은 새 UID. 폐기된 UID는 연결·콜백으로 복구하지 않는다.
- 다른 사용자와 공유한 식별자나 세션 참조, 알 수 없는 uid 테이블, 손상 이벤트, 거래/인증 기록은 실패로 차단. 보존 정책을 임의로 정해 삭제하지 않는다.
- 이 제한은 현재 실행기 범위이며 기록이 있는 고객의 삭제를 무기한 거부하는 최종 정책이 아니다. 별도 보존·분리 정책과 실행기를 계속 구현해야 한다.

## 실행 보호
- ACCOUNT_DELETION_EXECUTION=on과 ACCOUNT_DELETION_SINGLE_INSTANCE=on이 필요. 기본 OFF. 두 번째 값은 운영자가 단일 프로세스/인스턴스임을 실제 확인한 뒤에만 설정.
- 실제 DATA_DIR의 .storage-maintenance 점검 파일이 있어야 하고, 기존 일반 요청이 0건이어야 한다. 서버의 관리 진단에서 active_requests=0을 확인한다. 이 API는 점검 모드에서도 관리자 인증을 거쳐 접근한다.
- 관리자 토큰 + 활성 2FA 세션, 대상 접수번호 정확히 입력 + 영구 삭제 확인이 필수. 영구 삭제는 사용자가 직접 검토/실행해야 하며 이번 개발은 운영에서 실행하지 않았다.
- API: POST /v1/admin/account-deletions/{id}/execute, body {confirm_request_id,confirm_permanent:true}.
- 작업 중에는 점검을 유지한다. 실패해도 임의로 완료 처리하거나 점검을 해제하지 않는다. 동일 접수번호로 재시도한다.
- 작업 저널에 대상 식별자를 먼저 기록하고 프로필 폐기/이벤트 제거/DB/메모리 제거를 수행. 실패/재시작 시 이어서 처리. 완료 검사 후 저널 원문을 비우고 접수의 UID를 해시 참조로 대체.
- 삭제 후 프로필/기기 연결/본인 토큰/이벤트/DB/네이티브 시도/메모리 조건을 검사한다. 일부 단계가 실행돼도 검증 실패면 상태는 deleting으로 남는다.

## 상태와 접수증
- requested → reviewing → deleting → active_data_deleted.
- active_data_deleted는 활성 서비스 데이터 정리만 의미. backup_status=pending, full_deletion_complete=false.
- 백업/아카이브/저장장치 잔존 블록까지 파기됐다는 증거가 아니며 최종 completed 상태/API는 열지 않았다.
- 요청자에게 32바이트 난수의 읽기 전용 접수증을 발급. 서버에는 SHA-256만 저장, 90일 유효, 재발급 시 기존 접수증 폐기.
- POST /v1/me/deletion/status는 접수번호+접수증으로 최소 상태만 조회. UID·기기·은행·영수증 데이터와 변경 권한 없음. 요청별 바인딩·빈도 제한·no-store 적용. URL에 접수증을 싣지 않는다.
- 브라우저는 접수증을 로컬 저장소에 보관. 단순 요청/검토/전송 오류로 로그아웃하지 않는다. 서버가 활성 데이터 삭제 상태임을 확인하고 현재 계정이 접수 계정과 같을 때만 해당 브라우저의 인증을 정리.

## 검증
- check-account-deletion-executor: 인증/2FA/확인/점검/드레인 가드, 실패 후 새 프로세스 재개, 다른 사용자 데이터의 바이트 보존, 토큰 차단, 원장/공유 식별자 차단, 후속 조건 실패 시 완료 거부, 요청별 읽기 전용 접수증.
- check-account-deletion, check-deleted-identity, check-account-deletion-ui.cjs.
- check-receipt-settlement-flow, check-reward-identity와 모바일 bundle/check 회귀 통과.
- 모든 실제 삭제 동작은 TemporaryDirectory 내 가상 계정만 대상으로 실행.
