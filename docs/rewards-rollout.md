# 300P 영수증 보상 개발·검증 순서

## 지급 정책 변경 (2026-10-02)

관리자 지급 화면은 전체 신청의 대기·처리 중·지급 완료·반려 건수와 금액을 표시한다. 목록은 최근 200건이지만 합계와 장부 대조는 전체 기록을 사용한다. 신청별 차감·반환 금액과 사용자·영수증 연결을 비교하며 불일치는 자동 수정하지 않는다. 이 검사는 앱 내부 정합성 검사이고 은행 입금 확인이 아니다.

아래 초기 단계의 포인트 전용 정책을 변경한다. 승인 영수증 1건당 300P를 적립하고 300원 계좌 지급을 신청할 수 있다. 최소 누적 금액은 없다. 네이버페이는 발급 조건 확인 전까지 미제공이다.

계좌 지급은 수동이다. 관리자가 처리 시작 → 계좌 열람 → 외부 은행 송금 → 이체 참조번호 입력 순으로 진행한다. 지급 완료 버튼 자체는 송금하지 않는다. 반려는 실제 미송금 확인 후에만 가능하며 확보된 300P를 한 번만 복구한다.

실제 영구 저장과 재시작 보존 검증 후 `REWARD_BANK_PAYOUTS=on`으로 활성화한다. 별도 Fernet 키 `PAYOUT_ENCRYPTION_KEY`가 필요하며 DB 백업과 분리해 보관한다. 키를 잃으면 진행 중 신청의 계좌를 읽을 수 있으리라 보장할 수 없다. 이관 없이 키를 교체하지 않는다.

계좌는 암호화하고 완료·반려 시 운영 행에서 비운다. 과거 백업과 SQLite 잔여 영역까지 즉시 삭제되는 것은 아니다. 백업 접근과 보존은 별도 관리한다. 현재 운영 활성화와 실제 지급은 하지 않았다.

## 운영 백업·복구 (2026-10-02)

- `/admin/rewards`에 관리자 토큰을 입력하면 승인·검토 중 합산 포인트와 남은 접수 건수를 확인할 수 있다. 포인트를 현금 지급액으로 표시하지 않는다.
- 모집 상한은 `RECEIPT_REWARDS_MAX_CLAIMS`로 설정하며 기본 100건이다. 검토 중인 건도 한도를 예약한다.
- 백업 다운로드는 `GET /v1/admin/rewards/backup`이며 관리자 인증이 필요하다. 모집 OFF 상태에도 기존 DB가 있으면 사용할 수 있다.
- ZIP에는 SQLite 원장·검토 이력·추천 귀속, 남아 있는 영수증 원본, 파일별 SHA-256 검증값이 포함된다. 누락된 영수증이 있으면 불완전한 백업을 성공으로 반환하지 않는다.
- 이 ZIP은 **보상 데이터 전용**이다. `users.json`, 사용자 이벤트, 로그인 서명 비밀값과 운영 환경설정은 별도로 보관해야 계정까지 복구할 수 있다. 내려받은 ZIP은 암호화된 파일이 아니므로 접근 제한이 필요하며, 영수증 보관기한은 내려받은 백업에도 적용한다.
- 복원은 운영 경로가 아닌 **존재하지 않는 새 폴더**에만 수행한다:

  `python scripts/restore-rewards.py rewards-backup.zip NEW_DIRECTORY`

- 검증값·DB 무결성·영수증 참조 검사를 통과한 뒤 잔액과 이미지 표본을 대조한다. 실행 중 DATA_DIR을 덮지 않는다. 복원 결과를 운영 경로로 전환하는 작업은 별도 배포 절차다.
- 현재 SQLite와 파일 묶음 생성 동안 쓰기를 잠깐 잠근다. 파일럿 규모 기준이며 큰 이미지 저장소로 확장할 때는 객체 저장소와 별도 백업 작업으로 분리한다.
- 영수증 보관기한 정리는 서버 초기화 및 보상 저장소 접근 시 실행된다. 접근이 전혀 없는 기간에도 정해진 시각에 삭제하려면 별도 예약 실행이 필요하다.

## 원칙

- 첫 파일럿은 현금 300원이 아니라 앱 안의 `300P` 적립으로 운영한다.
- 포인트의 사용처와 환급 조건을 공개하기 전에는 현금처럼 표현하지 않는다.
- 추천을 통해 선택한 방문 매장만 대상이다. 배달과 임의 매장 영수증은 받지 않는다.
- 영구 저장소가 없으면 기능을 열지 않는다. 포인트 원장 유실 가능성이 있는 상태에서 보상을 약속하지 않는다.
- 보상 후기임을 화면과 향후 공개 후기에서 명확히 표시한다.

## 0단계 — 운영 기반

배포 전 필수 조건이다.

1. Render 영구 디스크를 `/data`에 연결하고 `DATA_DIR=/data`를 적용한다.
2. 재시작 전후 `rewards.sqlite3`, 영수증 파일, 사용자와 이벤트 파일이 같은지 비교한다.
3. `ADMIN_TOKEN`과 `GUEST_SIGNING_SECRET`을 운영 비밀값으로 설정한다.
4. 관리자만 원본 영수증을 볼 수 있는지 확인한다.
5. 개인정보 처리방침에 수집 항목, 목적, 보관 기간, 삭제 방법을 추가한다.

이 단계 전에는 `RECEIPT_REWARDS=off`를 유지한다.

## 1단계 — 폐쇄형 300P 파일럿

현재 구현 범위다.

- 추천 선택과 매장·메뉴·사용자를 하나의 귀속 ID로 묶는다.
- 최근 3일 이내 영수증만 접수한다.
- 하루 1건, 동일 이미지, 동일 승인번호, 동일 추천의 중복 접수를 막는다.
- 운영자가 영수증을 보고 승인하거나 사유와 함께 반려한다.
- 승인 원장은 수정형 잔액 대신 추가 기록으로 남긴다.
- 사용자는 `/rewards`에서 검토 중 포인트와 적립 잔액을 확인한다.

파일럿 규모는 30일 또는 승인 영수증 100건 중 먼저 도달하는 시점까지로 제한한다.

## 2단계 — 지급과 부정 사용 운영

1단계 지표가 통과한 뒤 개발한다.

- 포인트 사용처 또는 교환 수단을 확정한다.
- 사용자 본인 확인, 지급 실패, 취소와 회수 원장을 추가한다.
- 같은 카드·상호·금액·시각 조합, 편집 이미지, 반복 기기 패턴을 위험 신호로 표시한다.
- 원본 영수증 자동 삭제와 감사용 최소 정보 보존 작업을 배치로 실행한다.
- 관리자 권한을 단일 토큰에서 계정·역할 기반으로 바꾼다.

## 3단계 — 유입 실험

- 광고 문구는 “식당 추천을 받고 실제로 먹은 뒤 영수증 인증 시 300P”로 통일한다.
- 광고별 유입, 추천 시작, 매장 선택, 지도 이동, 영수증 접수, 승인까지 같은 캠페인 ID로 측정한다.
- 첫 실험은 지역을 제한하지 않되 예산과 일일 승인 건수에 상한을 둔다.
- 보상만 받고 떠나는 사용자를 구분하기 위해 7일 내 재방문과 두 번째 추천 선택을 본다.

통과 기준:

- 추천 시작 대비 매장 선택률 35% 이상
- 매장 선택 대비 지도·주문 이동률 50% 이상
- 이동 대비 승인 영수증률 15% 이상
- 승인 사용자 7일 재방문율 20% 이상
- 승인 1건당 총비용이 향후 매장 과금 예상액보다 낮음

## 4단계 — 가게 광고 상품

사용자 행동이 충분히 쌓인 뒤 시작한다.

- 노출 판매가 아니라 검증된 방문 또는 승인 영수증 기준으로 과금한다.
- 광고 매장은 일반 추천과 구분하고 추천 적합도 필터를 그대로 통과해야 한다.
- 매장 대시보드에는 노출, 지도 이동, 승인 방문, 재방문 의향만 제공한다.
- 최소 표본 이하의 매장 데이터는 개인을 추정할 수 없도록 숨긴다.

## 중단 기준

- 부정 접수율이 10%를 넘음
- 승인 1건 처리 시간이 3분을 넘음
- 7일 재방문율이 10% 미만
- 저장·원장 불일치가 한 건이라도 발생
- 보상 비용을 제외한 사용 가치가 인터뷰와 행동에서 확인되지 않음
