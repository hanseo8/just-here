# MY·지갑·포인트 사용처 기획안

작성: 2026-10-19 · 제안 단계. 운영 모집·지급 활성화나 제휴 체결을 뜻하지 않음.

## 결론
MY는 지금 도입한다. 교환몰은 실물 배송몰 대신 모바일쿠폰·제휴 가게 혜택으로 단계 도입한다. 고객의 현금성 보상과 가게가 제공하는 할인 혜택은 별도 원장·표시로 운영한다.

## 고객 메뉴
- 메인 상단 ‘내 보상’을 ‘MY’로 변경. 향후 하단 홈 / 가게 찾기 / MY는 전체 탐색 구조 검수 후 도입.
- MY 상단: 계정 연결 상태, 계정 복구·동기화 안내.
- 내 지갑: 사용 가능 P / 검토 중 P / 지급·교환 예약 P. 검토 중은 사용할 수 없고, 지급 완료 금액을 잔액에 다시 더하지 않는다.
- 주요 행동: 영수증 인증하기 / 보상 받기.
- 내 활동: 영수증 접수·반려 사유 / 지급 내역 / 내 쿠폰 / 저장한 가게 / 문의·개인정보 안내.
- 사용처는 계약·재고·정산이 준비된 항목만 노출. 준비 중인 브랜드 로고나 교환 버튼으로 이용 가능성을 암시하지 않는다.

## 화면 흐름
가게 선택 → 방문 → 영수증 제출 → 검토 중 → 승인·300P 적립 → 계좌 지급 또는 지원하는 교환 선택 → 처리 중 → 지급·발급 완료.
사진 업로드만으로 적립하지 않는다. 거절 사유·중복 신청·잔액 부족·만료·오프라인 상태를 각 단계에 표시한다.
현재 20계정·총 6,000원·계정당 1건 파일럿에서는 한 사람이 300P만 적립할 수 있다. 3,000P 이상 교환권을 주력으로 보여주면 목표에 도달할 수 없으므로 현 파일럿은 300P 계좌 지급을 유지한다. 반복 적립은 다음 파일럿의 예산·한도를 새로 승인한 뒤 설계한다. 기존 참여자의 지급 조건을 소급해 불리하게 바꾸지 않는다.

## 사용처 3가지
1. 계좌 지급: 이미 구현된 경로를 우선 사용. 수동 확인·송금·지급 완료 구분 유지.
2. 모바일쿠폰: 공급사 계약 후 상품 목록·가격·재고·발급·조회·취소 연동. 결제 비용과 수수료가 있어 포인트 발행 자체가 수익이 되지 않는다. 공급사의 실제 소액 상품 가용성을 확인한 후 교환 단위를 결정.
3. 지역 가게 혜택: 재방문 할인·사이드 제공 등 점주 부담 프로모션을 소수 가게와 시험. ‘포인트 차감 없이 받는 제휴 쿠폰’부터 시작하면 정산 복잡도가 낮다. 포인트를 매장 결제금액에 직접 쓰는 모델은 추후 별도 계약·정산·관련 요건 검토가 필요.

## 제휴 가게 파일럿 제안
- 3~5개 가게를 직접 모집하고 이용조건·기간·최소 주문·중복 할인·비용 부담·취소 정책을 서면 확정.
- 고객 쿠폰: 사용처 지점 / 제공 혜택 / 조건 / 기한 / 사용 전 확인.
- 점주: 로그인된 확인 화면에서 사용 처리. 시간 제한 토큰과 서버 검증으로 일회성 처리하며 화면 캡처만으로 사용 완료하지 않음.
- 광고료는 단순 노출보다 확인 가능한 유입·재방문 결과를 근거로 협의. 할인 비용·운영 수수료·부가 비용 부담 주체를 계약에서 분리.
- 일반 추천과 광고는 표시·측정 분리. 유료 입점이 긍정 리뷰나 검증 메뉴를 보장하지 않음.

## BM·측정
핵심 흐름: 추천 노출 → 지도 열기 → 영수증 승인 → 보상 수령 → 재방문 쿠폰 사용.
동일 고객의 재방문은 계정과 유효한 거래 증거로 확인하며, 쿠폰 클릭만으로 매출·방문을 주장하지 않는다.
운영 지표: 첫 승인까지 전환, 승인 1건당 총비용, 지급 완료율·소요시간, 부정/반려 비율, 보상 후 재이용, 가게별 쿠폰 실제 사용.
단위손익 = 광고·성과 수익 - 보상 비용 - 공급/송금 비용 - 심사·문의 비용 - 부정사용 손실. 포인트 소멸·미사용은 핵심 수익 가정에서 제외.

## 개발 순서와 통과 조건
1. MY 통합: 기존 인증·잔액·접수·지급 API를 사용. 잔액 이중 계산 없음, 타 계정 조회 불가, 모집 OFF에서도 내역 조회 정책과 안내 일관성 검증.
2. 지급 완결성: 실제 휴대폰 사진·키보드·스크롤 QA, 개인정보 처리, 서버 재시작 보존, 외부 백업·복구, 신청 중복 차단. 현 UI 및 빈 원장 복원 검증과 구분.
3. 제휴 쿠폰 파일럿: 점주 확인 도구·일회성 사용·취소·이력·만료. 실제 제휴 확정 후 노출.
4. 모바일쿠폰 API: 서버에서 잔액 예약 → 공급사 발급 → 결과 조회·확정. 타임아웃은 발급 여부 조회 후 처리하며 무조건 환불·재발급하지 않음. 실패 확정 시 한 번만 복원. 관리자 예외처리·일별 대사 필요.
5. 반복 적립 확장: 새로운 예산·계정별 한도 확정, 재방문·손익 검증 후 확대. 전국 사용처나 직접 결제 지갑은 이 단계 이후 판단.

## 외부 확인과 미확정
- 기프티쇼 비즈는 모바일쿠폰 API 연동을 안내한다. 우리 서비스 이용 승인·가격·최소 금액·취소·재고 조건은 아직 확인하지 않았다. https://biz.giftishow.com/external/down/api_qna.pdf
- Npay는 제휴사 포인트 전환과 본인인증 흐름을 안내한다. 일반 API 키만으로 우리 포인트가 Npay가 되는 것으로 설계하지 않는다. 우리 서비스 제휴·전환 가능 여부는 미확정. https://help.pay.naver.com/faq/content.help?faqId=11260

## 이번 결정 제안
개발 범위는 MY + 기존 지갑·접수·지급 내역 통합까지 우선 승인한다. 제휴 가게는 모집 자료·운영 조건부터 준비하고, 쿠폰몰 개발은 공급 계약과 실제 교환 가능 금액 확인 뒤 시작한다. 신규 유료 계약·지급·포인트 정책 변경은 별도 결정한다.
